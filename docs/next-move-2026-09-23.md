## What the project does

- Binance REST candles flow through PostgreSQL/TimescaleDB and dbt into technical features. Airflow schedules backfills and transformations.
- A separate WebSocket → Redpanda → feature-processor path publishes rolling trade features. These snapshots are currently informational for entry freshness; the technical/ML strategy does not require them.
- Technical rules, XGBoost predictions, and optional sentiment feed weighted signal fusion. The adopted live configuration disables sentiment to match historical replay, uses ML BUY threshold 0.55, a 24-hour position limit, and the BTC 200-day SMA regime gate.
- Historical evaluation supports chronological multi-symbol replay, rolling walk-forward training, cached probabilities, parameter sweeps, reports, and experiment comparison.
- Execution includes exchange filters, position sizing, portfolio risk limits, drawdown controls, OCO handling, heartbeat records, and an uncommitted persistent paper account and decision journal.

## Findings that change the priority

### 1. Historical regime decisions use information from later that day

`signals/regime.py:30` selects the final hourly close for each UTC date. The R1 function at line 56 assigns its classification to that same date. `backtest/experiment.py:_resolve_regime` computes this from all loaded bars, and `backtest/signal_cache.py:258` looks it up with the current intraday bar's date. Thus an early-day replay entry can depend on that evening's BTC close. Live computation instead sees the partial day available at runtime.

This is a code-path finding, not a quantified estimate of its effect on exp008. The recorded acceptance result needs reassessment after correction.

### 2. A failed refresh can allow entries with no current regime decision

`execution/bot_runner.py:run_once` retains the old regime dictionary on refresh failure. `signals/aggregator.py:143` blocks only an explicit RISK_OFF value; a missing current date permits BUY. Retaining yesterday's dictionary therefore does not guarantee the fail-safe behavior claimed in the runner docstring. Per-symbol candle freshness does not establish that a current BTC regime decision exists.

### 3. Data cadence and candle finality need attention together

The Airflow DAGs run daily at 00:05 and 00:15 UTC, independently. The bot requires candles and features no older than three hours. A ten-minute schedule offset also does not enforce successful backfill before feature generation.

The REST adapter drops exchange close-time information without filtering incomplete candles. Backfill inserts with `ON CONFLICT DO NOTHING` and resumes after the latest stored open time. If an unfinished candle is returned and stored, this path can retain its provisional values. Reproduce this with a synthetic API response before changing ingestion; also verify repair of historical gaps and provisional rows.

### 4. The preferred experiment command cannot pin an evaluation window

`cli experiment` exposes neither start nor end bounds. `backtest/experiment.py:run_experiment` loads all data and sets the replay interval from 1970 to the current time. The ledger's tuning/holdout rules therefore cannot be enforced through that command as currently implemented. The lower-level backtest command already has date bounds.

### 5. Live training is a separate, weaker reproducibility path

`signals/ml_model.py:train` concatenates per-symbol frames before splitting 80/20; the frames returned by `load_training_data` omit timestamps. This is not a globally chronological multi-symbol split. Live training also does not inherit the walk-forward 540-day window and frozen-parameter lifecycle simply by using `StrategyConfig`. Model provenance and the intended retraining policy must be established before claiming live/backtest parity.
